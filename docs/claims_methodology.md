## Claim 1: Pulse cannot reproduce a real patient's cardiac output/stroke volume

**Scripts/functions, file:line:**
- `src/patient_builder/patient_file.py:200-277` — `bcg_to_cardiovascular_modifiers()` (converts real BCG waveform features to Pulse's `VenousComplianceMultiplier`/`SystemicComplianceMultiplier`)
- `src/patient_builder/patient_file.py:122` — `ef_to_cardiovascular_modifiers()` (the EF-driven base multipliers, unchanged, layered underneath)
- `src/patient_builder/patient_file.py:83` — `build_patient_file()` (assembles the Pulse patient file; takes an optional `hr_baseline_bpm`, default `None`)
- `scripts/bcg_extract_subject14_features.py`, `scripts/bcg_extract_subject102_features.py` — R-J interval / I-J-K amplitude extraction from raw BCG signal
- `scripts/bcg_real_patient_validation.py`, `bcg_subject102_validation.py`, `bcg_real_patient_run.py`, `bcg_step1_diagnostic.py`, `bcg_hr_baseline_experiment.py` — build/run/counterfactual scripts
- Full write-up with every number: `docs/bcg_validation_note.md`

**Inputs, exact source:**
- Real: subject 14's/102's demographics (age, sex, height, weight), EF (M-mode echo), and BCG waveform (R-J interval, I-J/J-K amplitude) — all from the Zhan et al. 2025 Multi-Pathology BCG Dataset (figshare 10.6084/m9.figshare.28416896), a published, externally sourced dataset, not generated by this project.
- Manual, not measured: `scenario_type`/`severity` (`acute_deterioration`, severity=0.35 for both subjects) — assigned by the analyst from the real EF/diagnosis, because a single-session recording has no 21-day wearable trend for Model 1 (the scenario classifier) to run on. Model 1 is **not** exercised or validated by this claim at all.
- Approximation flagged in the source doc: BCG amplitude units are the dataset's own relative units with no published calibration factor; the venous/systemic-compliance reference point is the *other* one of only two available subjects (n=2), not a population norm.
- Subject 102's own session-derived HR (52.8 bpm) disagreed with its own clinical sheet (115 bpm) by 2.15×, unexplained by the source paper — the clinical-sheet value (115) was used as ground truth instead, a deliberate, documented substitution, not an oversight.

**Exact calculation, plain English:** `bcg_to_cardiovascular_modifiers()` turns R-J interval into a 0–1 "deficit" relative to the other subject's R-J value, then maps that deficit linearly onto a compliance multiplier (floor 0.6); same for the averaged I-J/J-K amplitude. These multipliers, plus the EF-driven multipliers from the already-existing `ef_to_cardiovascular_modifiers()`, configure a Pulse physiology simulation. Pulse then computes heart rate, stroke volume (SV), and cardiac output (CO) as simulation outputs — nothing about SV/CO is set directly; they emerge from the underlying circuit model.

**Ground truth for comparison:** subject 14's real SV/CO come from the dataset's own echo-derived EDV/ESV (SV = EDV − ESV) and HR; subject 102's the same. Real CO is computed as SV × HR (not separately measured).

**How verified (not re-run — Docker unavailable in this environment):** I read the actual recorded output file `data/bcg_validation/subject14/full_results.csv` directly. Row at `Time(s)=0` reads `HeartStrokeVolume(mL)=65.724343`, `CardiacOutput(mL/min)=4749.877424` — matching the write-up's cited 65.72mL/4749.9 exactly, confirming these are genuine simulator outputs already on disk, not invented numbers.

**Actual result (default configuration, the one every production code path actually uses — confirmed by grep: no call site in `batch_runner.py`, `projection.py`, `api/services.py`, or `validate_phase2.py` passes `hr_baseline_bpm`):**

| Subject | HR ratio (sim/real) | SV ratio | CO ratio |
|---|---|---|---|
| 14 | 0.94 | **0.58** | **0.54** |
| 102 | 0.63 | **0.87** | **0.55** |

**What would have contradicted this claim:** SV and CO ratios both landing close to 1.0 (say, within ±15%) for both subjects. Instead they land 42–46% short on CO for both subjects, and 13–42% short on SV — a wide, not uniform, gap.

**Why this reading is considered correct, not a data-entry error:** the note traces the SV shortfall stage-by-stage using the engine's own log — 71.3% of it is already present from the anthropometric baseline alone (age/height/weight), before EF or BCG data ever enters the model. A height-only counterfactual (160cm vs. 175cm, same weight, everything else held at zero) produced the *identical* 79.46mL SV in both cases — ruling out height as the cause and pointing at Pulse's generic population-level circuit tuning as the dominant driver. A separate experiment (forcing HR to the real value directly) made HR match almost exactly but made SV match *worse* in both subjects — a real physiological trade-off (less diastolic filling time), not a sign the fit could easily be corrected by tuning one input harder.

**Limitations / what this does NOT show:**
- **n=2.** No cohort-level claim is possible or made.
- Not a trend/change-tracking test — both subjects are single-session snapshots; whether simulated Δ tracks real Δ over time is explicitly untested (no second time-point exists for either subject).
- BCG substitutes for the originally-planned PPG modality; it measures a different mechanical signal (whole-body recoil, not peripheral blood-volume pulse).
- The R-J→venous-compliance and amplitude→systemic-compliance mappings are each a single literature citation, not independently validated against outcomes.
- I did not re-run the Docker/Pulse simulation myself this session (container not running here) — verified instead by reading the already-produced output file directly, which is a weaker check than re-executing the run, though it does confirm the numbers are real recorded simulator output and not fabricated prose.

## Claim 2: The system detects a deteriorating trend (21-day synthetic stress test)

**Scripts/functions, file:line:**
- `scripts/synthetic_deterioration_stress_test.py:94-132` — `build_trend()` (constructs the synthetic 21-day trend)
- `scripts/synthetic_deterioration_stress_test.py:135-190` — `main()` (the expanding-window classification sweep)
- Reused, not reimplemented: `src/data_synthesis/generate_wearable_trends.py`'s `_trend_curve()`, `SCENARIO_SIGNAL_DELTAS` (imported directly, line 43-49 of the stress-test script); `src/scenario_classifier/features.py`'s `build_inference_features()`/`feature_columns()`
- Models loaded: `models/scenario_classifier.joblib`, `models/severity_regressor.joblib` — the actual production models, unmodified

**Inputs, exact source:**
- Real, one number per subject: resting HR baseline (subject 14: 77 bpm; subject 102: 115 bpm) and EF (34.7%/35.1%), both from `docs/bcg_validation_note.md`'s same two BCG subjects.
- Synthetic, everything else: the entire 21-day trajectory past day 0 is generated by the same formula `generate_wearable_trends.py` uses for training data, seeded (1400/1020, fixed) so it's exactly reproducible, forced into `"deteriorating"` mode (not the original function's own probabilistic mode assignment) with `scenario_type="acute_deterioration"` hard-coded — this is a deliberately constructed stress case, not a random draw that could have come out "recovering."
- SpO2/steps/sleep/HRV baselines are population means (`reference_stats.yaml`), not measured for either subject — only resting HR and weight are real-anchored, following the same precedent `generate_wearable_trends.py` already uses for weight.
- `nt_probnp_pg_ml` uses the fixed Tier-1 fallback value (100.0) — no real BNP measured for either subject.

**Exact calculation, plain English:** for each window length n=7..21 days, take only the first n days of the (synthetic) trend, run it through the exact same feature-extraction and prediction code the live API uses (`build_inference_features()` → `clf.predict()`/`reg.predict()`), and record the predicted `scenario_type` and `severity`. This produces a day-by-day sweep of what the classifier *would* have said if a real deployment's wearable-sync had stopped accumulating at that many days — something production never actually does (production only ever predicts once, at the full 21-day window; this sweep is a diagnostic tool built on the same prediction code, not a second production path).

**Ground truth / "correct" answer:** by construction, this trajectory should read as `acute_deterioration` at every window once enough of the trend has accumulated, since that's the label it was built to represent — there is no independently measured deterioration event to check against (this is fully synthetic past day 0).

**How verified:** re-ran the script directly this session (pure Python/scikit-learn, no Docker needed). Output:

| Day range | Subject 14 | Subject 102 |
|---|---|---|
| 6–10 | classified `fluid_overload` | classified `acute_deterioration` (correct throughout) |
| 11–20 | classified `acute_deterioration` (correct) | `acute_deterioration` |
| Severity at day 20 | 0.866 | 0.878 |
| Severity monotonically non-decreasing? | **No** (dips at day 9: 0.456→0.342) | **No** (dips at day 15: 0.613→0.601) |

Both subjects converge to the correct `acute_deterioration` label by the end of the window, and severity trends upward overall — but **subject 14 specifically is misclassified as `fluid_overload` for 5 straight days (6–10)** before correcting at day 11; subject 102 is never misclassified.

**What would have contradicted this claim:** the classifier never reaching `acute_deterioration` at all by day 20, or severity trending flat/downward overall. Neither happened — the claim "the system eventually detects the trend" holds. The narrower claim "the system detects it cleanly/immediately" does **not** hold for subject 14.

**Limitations / what this does NOT show:**
- **Does not show real deterioration is detected in a real patient** — the entire post-day-0 trajectory is synthetic; only two numbers (HR baseline, EF) are real. The script's own docstring states this explicitly.
- **Does not reflect a production failure mode** — production's own live pipeline (`src/api/services.py`) only ever evaluates the classifier once, at the complete 21-day window, never at partial windows. The Day 6–10 misclassification is a property of this diagnostic sweep applying the model outside the window length it was designed for, not something a real deployed patient would ever trigger.
- The specific misclassification is patient-parameter-specific, not universal: subject 102, run through the identical code with different real anchor values, does not show it.

## Claim 3: Our risk scores do not predict real outcomes (MIMIC-IV, Zigong, MAGGIC-11)

**Scripts/functions, file:line:**
- `src/analytics/risk_score.py:95-102` — `_baseline_deficit_component()`; `:105-148` — `compute_risk_score()` (the actual production function, called unmodified everywhere below)
- `scripts/mimic_outcome_validation.py:52` `bootstrap_auc_ci()`, `:72` `compute_baseline_deficit_only()`, `:81` `main()`
- `scripts/zigong_outcome_validation.py:60` `compute_baseline_deficit_only()`, `:69` `bootstrap_metric_ci()`, `:88` `main()`
- `scripts/train_clinical_only_variant.py:35` `main()` (trains a new clinical-features-only variant of Model 1)
- `scripts/zigong_clinical_only_model_validation.py:51` `main()` (runs that variant on Zigong)
- `src/analytics/benchmark_scores.py:133` `compute_maggic_score()`
- `scripts/zigong_maggic11_validation.py:75` `compute_maggic11()`, `:100` `main()`

**Inputs, exact source and approximations:**
- **MIMIC-IV**: real ICU admission-level MAP readings (first 24h), real `hospital_expire_flag` (in-hospital death) — from BigQuery, `physionet-data.mimiciv_3_1_*`. I could **not** re-run this myself: the extract file (`data/raw/mimic/hf_admission_outcomes.csv`) is real, DUA-protected patient data and is not present in this environment/repo (gitignored by design). Verified instead by reading the already-produced `data/mimic_outcome_validation/summary.md` directly.
- **Zigong**: real hospital EHR data (PhysioNet, DUA-signed), `dat.csv`/`dat_md.csv`. Real fields used directly: `map`, `LVEF`, `NYHA.cardiac.function.classification`, `brain.natriuretic.peptide` (BNP), Charlson comorbidity flags, `systolic.blood.pressure`, `creatinine.enzymatic.method`. **Approximations, all flagged in the scripts themselves:** `age` = `ageCat` bin midpoint (e.g. `(59,69]`→64), not real continuous age; `nt_probnp_pg_ml` in the Model-1 clinical-only test = Zigong's raw BNP value with **no unit conversion** (BNP and NT-proBNP are different assays with different reference ranges — this project has no validated conversion, and none was invented; explicitly labeled an invalid substitution in every script/doc that uses it); beta-blocker/ACEI-ARB use for MAGGIC-11 derived from `dat_md.csv`'s drug-name list (Metoprolol=beta-blocker, Benazepril=ACEI, Valsartan=ARB), not a direct field.
- Cleaning applied identically across all Zigong scripts: drop rows with `pulse==0`, `respiration==0`, `systolic.blood.pressure==0`, `height<1.0m`, `BMI>60` (7 of 2008 dropped → n=2001).
- Outcome (Zigong, all three tests): composite = `death.within.6.months==1 OR re.admission.within.6.months==1`, a real, recorded hospital outcome, not derived by this project.

**Exact calculation, plain English:**
1. `baseline_deficit_score` (MIMIC + Zigong): `compute_risk_score()` is called with every *acute* input (`hr_rise`, `map_drop`, `co_drop_pct`, `compensation_flag=1`, `instability_flag=0`) fixed at its neutral value, which forces the acute half of the formula to exactly 0 — verified by an `assert` in the code itself (`mimic_outcome_validation.py:77`, `zigong_outcome_validation.py`) — so `risk_score = baseline_deficit_score` exactly, a pure function of real measured MAP.
2. Model 1 clinical-only variant: a brand-new `RandomForestRegressor`/`RandomForestClassifier`, trained from scratch on the 5 clinical columns only (`age, sex_male, bmi, ejection_fraction_pct, nt_probnp_pg_ml`), same hyperparameters as production, then run on Zigong's approximated 5-field vector.
3. MAGGIC-11: the real, externally-published, hand-verified MAGGIC formula (`compute_maggic_score()`), with 2 of its 13 inputs (current smoker, HF-diagnosis duration) structurally absent from Zigong and excluded (not defaulted) by passing the one parameter value that makes each term's contribution exactly zero.
4. In every case: `roc_auc_score`/`average_precision_score` from **scikit-learn** (`sklearn.metrics`) computes AUC/PR-AUC of the score against the real binary outcome; a 95% CI is built by percentile-bootstrap resampling (2000 resamples, `numpy.random.default_rng(seed=42)`), resampling (score, outcome) pairs together and re-computing the metric each time.

**Train/test splitting:** the MIMIC/Zigong `baseline_deficit_score` tests and the MAGGIC-11 test use **no train/test split at all** — `compute_risk_score()`/`compute_maggic_score()` are fixed, hand-tuned formulas with no parameters fit on this data, so there is nothing to overfit; the entire real cohort is evaluated once. The Model 1 clinical-only variant *is* trained, on **synthetic** data only, via `split_patients()` (`src/scenario_classifier/train.py`, patient-level stratified 70/15/15, seed=42) — the same split the production model uses — then applied to Zigong (real data) purely at inference time, never trained on it.

**Actual results, re-confirmed by reading the artifact files on disk this session (not from memory):**

| Test | n | AUC (95% CI) | PR-AUC |
|---|---|---|---|
| `baseline_deficit_score`, MIMIC-IV | 17,129 | **0.596** (0.585–0.608) | not computed |
| `baseline_deficit_score`, Zigong (complete-case) | 625 | **0.533** (0.490–0.575) | 0.463 |
| `baseline_deficit_score`, Zigong (full cleaned) | 2,001 | 0.548 (0.525–0.573) | 0.457 |
| Model 1 clinical-only variant, Zigong | 625 | **0.517** (0.473–0.562) | 0.419 |
| MAGGIC-11, Zigong | 622 | **0.604** (0.559–0.649) | 0.496 |

**What would have contradicted this claim:** AUCs clearly and consistently above ~0.7 with CIs excluding 0.5 by a wide margin, matching or beating the literature's MAGGIC range. Instead: MIMIC-IV shows a modest-but-real signal (CI excludes 0.5), both Zigong tests of this project's own mechanisms sit with a CI straddling 0.5 (indistinguishable from chance), and the externally-published MAGGIC-11 does noticeably better (0.604) than either of this project's own mechanisms on the identical cohort and outcome.

**Why this precise wording matters — a correction to how this claim is often stated:** "our risk scores do not predict real outcomes" is accurate for the two Zigong tests of this project's own mechanisms (`baseline_deficit_score`, Model 1's clinical component) but is **too strong** if applied to MIMIC-IV, where the same mechanism scored 0.596 with a CI that excludes chance — modest, not "no better than chance." It is also not accurate to fold MAGGIC-11 into "our risk scores don't predict outcomes" at all: MAGGIC-11 is an external, published score, not part of this project's own architecture, and it's the best-performing score in this table.

**Limitations / what this does NOT show:**
- Explicitly, in every script's own docstring: **this tests whether a baseline snapshot predicts a future outcome — it does NOT test whether the system detects a day-by-day deteriorating trend**, which is the actual designed use case and remains untested against any real longitudinal data.
- The MIMIC/Zigong cohorts are hospitalized, acutely-ill populations at the moment of measurement — not this project's target outpatient/home-monitoring population.
- `map`/`map_start` here is one real, single-timepoint clinical vital — not a Pulse-simulated baseline, which is how the same formula is used everywhere else in this project.
- MAGGIC-11 needs creatinine and NYHA class — lab-draw and clinical-encounter data, not anything obtainable from a wearable. Whatever MAGGIC-11's result means, it says nothing about a wearable-only early-warning system's viability.
- I could not personally re-run the MIMIC-IV extraction/scoring in this environment (no BigQuery access, no local copy of the protected extract) — verified only by reading the already-produced summary file, not by re-executing the query and computation myself.

## Claim 4: The problem is solvable in principle (Zigong-native model, AUC 0.667)

**Scripts/functions, file:line:**
- `scripts/zigong_native_risk_model.py:86` `clean()`, `:94` `main()` (the entire pipeline: field selection, split, model, evaluation, feature importances)

**Explicitly, this is a separate, standalone exploratory analysis — it is not part of HeartGuard AI's production pipeline, does not use `risk_score.py` or Model 1, and does not feed back into either.**

**Inputs, exact source:** all real Zigong fields, no synthetic data at all. 65 of 67 candidate fields kept after checking missingness on each individually (<15% threshold): 8 vitals, NYHA class, Killip grade, `type.of.heart.failure`, 17 Charlson comorbidity fields (16 binary + `CCI.score`), 22 CBC values, 7 coagulation values, 5 renal-chemistry values, `admission.way`, `visit.times`, and BNP. Two dropped: `LVEF` (68.38% missing — checked, not assumed) and `leukemia` (0% missing but a single constant value across the entire cohort — zero variance, uninformative despite being "complete"). 315/2001 rows (15.7%) needed median imputation on at least one already-low-missingness field — never on `LVEF`.

**Exact calculation, plain English:** categorical fields are numerically encoded (NYHA/Killip as ordinal 1–4; `type.of.heart.failure` one-hot; `admission.way`/`type.II.respiratory.failure` as 0/1 flags — this specific one was caught failing on the first run because it's stored as the strings `"NonTypeII"`/`"TypeII"`, not already 0/1, and was fixed before the reported result). A `RandomForestClassifier` predicts the same composite outcome (`death.within.6.months` OR `re.admission.within.6.months`) directly as a binary classification target — unlike the severity-regression proxy used in Claim 3's Model-1-based tests, this model is trained specifically for this classification task.

**Train/test splitting, in detail:** a single stratified 80/20 split on the composite outcome (`sklearn.model_selection.train_test_split`, `random_state=42`) is made **before** any model selection — train n=1,600, test n=401. A small hyperparameter grid (`n_estimators`∈{300}, `max_depth`∈{4,8,None}, `min_samples_leaf`∈{1,5,20}) is searched via 5-fold cross-validation (`GridSearchCV`, `StratifiedKFold`) **on the training 1,600 only**. The held-out 401 test patients are touched exactly once, after the best hyperparameters are chosen, to compute the one reported number.

**Actual result:** train (in-sample) AUC=1.000 — expected for an unconstrained RandomForest evaluated on its own training data with `min_samples_leaf=5`, not a bug, and explicitly not the reported number. **Held-out test (n=401): AUC = 0.667 (95% CI 0.611–0.721), PR-AUC = 0.605** vs. 0.414 baseline event rate.

**Feature importances (top 5 of 66): `urea` (3.13%), `uric.acid` (3.12%), `glomerular.filtration.rate` (3.10%), `D.dimer` (2.79%), `creatinine.enzymatic.method` (2.74%)** — renal function and coagulation markers, not any HF-specific echo/biomarker field. No single field exceeds ~3.1% importance — a flat distribution across many moderately-informative fields, not one dominant predictor.

**What would have contradicted this claim:** an AUC indistinguishable from chance (like Claim 3's results), which would suggest no real signal exists in this population/outcome pairing at all, regardless of which fields are used. Instead, a properly-trained model using different, richer fields reaches AUC 0.667 — clearly above both risk_score.py's and Model 1's ~0.5–0.55 Zigong results, and within/above the literature's LACE-index range (0.56–0.65).

**Why "solvable in principle" is the correct, narrow framing — and why the professor should read the feature list before accepting a stronger claim:** the fields carrying the signal (renal chemistry, coagulation, CBC/inflammatory markers) are **lab-draw values obtained by a blood test during a hospital admission** — they are not measurable by a consumer wearable, and they are not part of this project's EF/NYHA/BNP-based architecture. The flat, renal/coagulation-dominated importance pattern suggests this model is picking up **general acute-illness severity**, a different and broader construct than the HF-specific deterioration this project's Model 1/`risk_score.py` are designed to detect. This result demonstrates that *some* real signal for this exact outcome exists in Zigong's data — it does **not** demonstrate that HeartGuard AI's specific wearable-and-EF-based design could ever reach it, and it does not test the actual product's early-warning use case at all (this is a one-shot baseline classification, not a trend/trajectory model).

**Limitations / what this does NOT show:**
- Not part of the production pipeline; a standalone benchmark only.
- The train/test AUC gap (1.000 → 0.667) is large — a real, disclosed overfitting signal, not hidden by reporting only the favorable train number.
- Complete-case handling of the remaining ~15.7% row-level missingness used light imputation (median), which is a departure from the "no imputation, complete-case only" discipline applied elsewhere in this project's Zigong work (§7.Y/AA/CC) — a deliberate, disclosed choice for this specific exploratory script, not an inconsistency to hide.
- Same population caveats as Claim 3 (hospitalized, acutely-ill population; composite outcome mixes death and readmission).
- Does not test whether the *specific fields this project can actually collect* could reach this AUC — that is precisely the negative finding in Claim 3.

## What earlier summaries stated that the code does NOT actually support, or that I could not verify

1. **"Subjects 14 and 102" both show the Day 6–9/6–10 misclassification.** They do not. Only subject 14 does (days 6–10, confirmed by rerunning the script this session). Subject 102 is classified correctly (`acute_deterioration`) from day 6 onward with zero misclassification. Any phrasing that describes this as a general property of the stress test rather than a subject-14-specific finding is not supported by the code's actual output.

2. **The "45–55% gap" applies to cardiac output specifically, not uniformly to stroke volume.** CO ratios are 0.54/0.55 for the two subjects (45–46% short — this part is accurate). SV ratios are 0.58/0.87 (13–42% short) — much more variable, and subject 102's SV match (0.87) is actually fairly close. A claim that states "cardiac output/stroke volume" both sit in a single 45–55% band overstates the SV finding's consistency.

3. **"Our risk scores do not predict real outcomes" is too strong as a blanket statement.** It holds for the two Zigong tests of this project's own mechanisms. It does not hold for the same mechanism's MIMIC-IV result (AUC 0.596, CI excludes 0.5 — modest but real, not chance). Stating this as one uniform finding across all three real-outcome cohorts is not what the numbers show.

4. **MAGGIC-11 is sometimes discussed in the same breath as "our risk scores," which is a category error.** It is an external, independently-published score (Pocock et al. 2013), re-verified against its own literature, not part of this project's architecture — and it is the best-performing score of the four in the comparison table. Grouping it with `risk_score.py`/Model 1 as evidence "our scores don't work" is not accurate.

5. **"The problem is solvable" (Claim 4) has, in places, been summarized without the feature-importance caveat attached.** The 0.667 AUC number on its own, without noting that it is driven by renal/coagulation lab values unavailable to a wearable-based system, invites the reader to conclude more than the result supports — that this project's own architecture could reach this number with more data, which the feature list does not establish.

6. **The MIMIC-IV result (Claim 3) could not be independently re-verified by me this session** — the underlying real-patient extract is not present in this environment. I read the existing summary artifact rather than recomputing it. Any claim resting on this number should note it is one step further from direct verification than the Zigong/BCG results, which I did re-read from on-disk artifacts or rerun directly.

7. **The BCG runs (Claim 1) were not re-executed this session** — Docker/Pulse is not running in this environment. I verified the cited numbers by reading the already-produced `full_results.csv` output file directly (confirmed it contains the exact cited values), which is real evidence the numbers weren't invented, but is not the same standard of verification as re-running the simulation myself.
