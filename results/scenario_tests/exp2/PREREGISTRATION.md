# Experiment 2 pre-registration: scenario test with an in-distribution EF band

**Committed before any Experiment 2 Pulse run.** The commit that adds this file is the
pre-registration. Experiment 1 (`results/scenario_tests/expected_outcomes.md`, commit `38c3520`)
and all its results stay as they are; Experiment 2 is reported beside it, never in place of it.

Framing is the same as Experiment 1: this checks how the pipeline responds to controlled synthetic
patient stories. It is not clinical validation.

## 1. Question

In Experiment 1, the classifier's day-by-day scenario label was correct on 17.6% of patient-days,
and "deconditioning" was predicted on 71.5% of days. The likely cause was distribution shift:
the cohort's neutral EF band (48–57%) sits below the training `stable` class (EF mean 61.2,
5th–95th percentile 54.9–67.5) and near the `deconditioning` mean (50.5). On each patient's flat,
pre-story baseline, the frozen classifier labels P01–P04 `deconditioning`
(`results/scenario_tests/posthoc/ood_check.json`).

**Experiment 2 asks: when the cohort starts inside the training distribution, how do label
accuracy, detection and false alerts change, and does the Pulse-based alert still trail the
classifier's own severity?**

## 2. What changes (and nothing else)

| | Experiment 1 | Experiment 2 | Why |
|---|---|---|---|
| EF | 48–57% (P01=48 … P10=57) | **58–67%** (each patient +10 points) | Moves every patient inside the training `stable` EF range. On flat baselines, all 10 are then labelled `stable` (probability 0.93–1.00) instead of 4/10 `deconditioning`. |
| P07 onset | Days 10–12 ramp, 0.20→0.40, held to day 21 | **Days 4–6** ramp, 0.20→0.40, held to day 21 | See §2.2. |
| Day 1 | First monitored day is `run_initial()` | **One unscored warm-up day** before monitored day 1 | See §2.1. |
| Seeds | 42–44 (dev), 45–47 (held-out) | **48–53**, never used before | Fresh noise draws; no rule is selected in Experiment 2, so all six are evaluation seeds. |

Everything else is the same as Experiment 1. That covers the 10 stories and their schedules
(except P07's timing), demographics, baseline wearables, NT-proBNP (200–290 pg/mL), expected
groups, expected labels and severity caps.

Generated by `src/evaluation/scenario_tests/build_cohort_exp2.py`, which reuses
`build_cohort.py` unmodified. Output: `config/scenario_tests/cohort_exp2.yaml`. A diff against
`cohort.yaml` differs only in `baseline_clinical_report.ejection_fraction_pct` (all 10),
P07's `monitored_day_schedule`, and `meta`.

### 2.1 Day-1 fix (test harness only)

In continuous mode, the pipeline's first call is `run_initial()`. It applies only the base
`CardiovascularMechanicsModification`, with no scenario extras and no Exercise
(`docs/research_flags_evaluation.md` §7.1). In Experiment 1, day 1 of every series was therefore
a different kind of run from days 2–21 (every day-1 row has `simulation_time_s = 660`).

Fix: `run_patient_seed.py` reads `meta.warmup_days` (1 in Experiment 2) and first runs one warm-up
day with a reading at the patient's baseline wearable levels (normal noise). That day is not
scored and not written to the CSV. Monitored days 1–21 are then all resumed runs. When
`warmup_days` is absent (Experiment 1's cohort file), behaviour is unchanged.

**No system code changes**: not `run_initial()`, not `continuous_state_pipeline.py`, nothing
under `src/api/`, `src/pulse_runner/`, `src/analytics/` or `src/scenario_classifier/`.

### 2.2 P07 onset: day 10 → day 4

P07's acute onset moves from days 10–12 to days 4–6. Nothing else about P07 changes: the same
3-day ramp of `severity_target` from 0.20 to 0.40 (0.267, 0.333, 0.400), the same 50% step-count
drop phased in over the same window, held at 0.40 to day 21, and the same `acute_onset` /
`acute_held` events.

Why: the primary detection rule is now the strict one (§4), so any alert before onset counts as a
miss. Every other should_catch story starts on day 4. With a day-10 onset, P07 had nine pre-onset
days on which an unrelated alert could fire first, which happened in 6/6 Experiment 1 seeds
(first HIGH on days 2–5). Its strict result (0/6) therefore measured exposure time more than its
response to the deterioration. Moving the onset to day 4 gives all five should_catch stories the
same three pre-onset days. Pre-onset false-alert behaviour is still measured by the three
should_stay_quiet patients.

## 4. Outcomes and definitions

**Change made after the dry run (§5), before any Experiment 2 Pulse run.** The first draft of
this file made strict detection (the first alert must fall on or after onset) a primary outcome.
The dry run then showed that P06, P07 and P10 get exertion labels on days 1–3 in 7 of 15 dev-seed
series, driven by the deliberate day-1 step in their stories. Under the strict rule, one
pre-onset alert turns a series into a miss even if the system also alerts throughout the
deterioration, so the strict rule mixes two different failures into one number. Detection and
pre-onset alerting are therefore now separate co-primary outcomes, and strict detection is kept
as a secondary outcome. Experiment 1 is reported the same way (reference values below). No
Experiment 2 Pulse output existed when this change was made.


Series = one patient × one seed (30 should_catch series, 18 should_stay_quiet series, 12
edge-case series). Onset day = first day with an `event` in the schedule (day 4 for all five
should_catch stories). Systems are as in `ablation_eval.py` / `ablation_baselines.py`.

**Primary** (deployed system = `decide_alert()` level ALERT):

1. **Sensitivity (co-primary)**: should_catch series with **any** alert on or after onset day
   (k/30, Wilson 95% CI).
2. **Pre-onset alert rate (co-primary)**: alert days per 100 pre-onset patient-days across the
   should_catch series (days before onset), plus the number of should_catch series with any
   pre-onset alert (k/30).
3. **False alerts per 100 patient-days** in the should_stay_quiet group, with bootstrap 95% CI.
4. **Day-by-day label accuracy**: predicted label = story's expected label, over all 1,260
   patient-days (Experiment 1's 17.6% definition).

**Secondary**:

- **Strict detection**: should_catch series whose **first** alert is on or after onset day.
- should_stay_quiet series with no alert at all.
- The same metrics for Pulse risk bucket HIGH, classifier severity > 0.55 (frozen), classifier
  severity > 0.15, the exertion-label rule and the weight rule (≥ 2 kg in 3 days).
- Label accuracy with pre-onset days scored as `stable` (Experiment 1: 19.8%).
- Per-patient results; P02/P03 described, not scored (as in Experiment 1).
- Failed Pulse days are reported both as alert and as no-alert, as in Experiment 1.

Experiment 1 reference values, deployed system, all six seeds (recomputed with
`ablation_eval.series()`; identical with failed days counted as alert or as no alert):
sensitivity 21/30; pre-onset alerts 40 of 126 pre-onset patient-days (31.7 per 100), in 7/30
series; strict detection 14/30; false alerts 8.7 per 100 patient-days; label accuracy 17.6%.
Experiment 1's P07 had 9 pre-onset days (onset day 10) against 3 in Experiment 2, so its share of
pre-onset days differs; the rate per 100 pre-onset days is the comparable figure.

## 5. Classifier-only dry run (disclosed)

Before writing this file, the Experiment 2 cohort was run **through the classifier only, with no
Pulse**, on **development seeds 42–44**, to see which labels each story produces. Seeds 48–53
were not dry-run: their labels are fully determined by the classifier, so dry-running them would
reveal the evaluation result before the experiment.

Tool: `src/evaluation/scenario_tests/exp2_dry_run.py`. It regenerates the exact wearable readings
`run_patient_seed.py` stores (same sha256-derived RNG, draw order and noise) and classifies each
day from the latest 21 readings. Faithfulness check: on Experiment 1's cohort and seeds 42–47, it
reproduces **1,260/1,260** saved labels and the 17.62% accuracy. Output:
`results/scenario_tests/exp2/dry_run_dev_seeds_42_44.json`.

**Result (seeds 42–44, 630 patient-days):** label accuracy **38.4%** (Experiment 1, same seeds

## 6. Predictions (committed before the Pulse runs)

**Mechanism.** Pulse exertion (Exercise) fires only on `cardiac_stress` or
`acute_deterioration` labels (`EXERCISE_SCENARIO_INTENSITY_FACTOR`). In Experiment 1, a series
reached HIGH **only if** it had an exertion label: 30 of 32 series with one went HIGH, 0 of 28
without one did. The first HIGH came 0–1 days after the first exertion label in 23 of 30.
Predictions below assume the same link: **first alert ≈ first exertion-label day (+0–1)**.

**Two things could break that link**, so the numbers below are ranges:

- With EF 10 points higher, Pulse's structural deficit is smaller (`ef_to_cardiovascular_modifiers`,
  EF > 40 branch). Experiment 1's HIGH days were mostly driven by the baseline mechanism, so fewer
  exertion days may convert into HIGH. If that happens, detection and false alerts fall together.
- With the warm-up day, an exertion label on monitored day 1 now gets real Exercise. In
  Experiment 1 it got none.

**Predictions for seeds 48–53** (dev-seed dry run scaled ×2, then widened):

| Outcome | Experiment 1 | Dev dry-run implication (15 or 9 series) | **Predicted, Experiment 2** |
|---|---|---|---|
| Label accuracy (primary definition) | 17.6% | 38.4% | **30–45%** |
| Label accuracy, pre-onset = stable | 19.8% | 43.0% | 35–50% |
| **Sensitivity, deployed (co-primary)** | 21/30 | ≤ 12/15 (P05 0) | **18–26/30** |
| **Pre-onset alert rate, deployed (co-primary)** | 31.7 / 100 pre-onset days; 7/30 series | exertion labels on 10 of 45 pre-onset days, in 7/15 series (P06 3, P07 2, P10 2) | **10–30 / 100 pre-onset days; 6–14/30 series** |
| Strict detection, deployed (secondary) | 14/30 | ≤ 5/15 (P04 3, P07 1, P10 1; P06 0 because its first exertion label is on day 3; P05 0) | **6–12/30, likely lower than Experiment 1** |
| P05 detected (any rule using Pulse) | 1/6 | no exertion label in any seed | **0–1/6** |
| should_stay_quiet series with no alert | 10/18 | P01 and P09 no exertion label; P08 exertion days 9–20 in all seeds | **11–13/18**: P01 and P09 mostly silent, P08 alerts in most or all seeds |
| False alerts / 100 patient-days, deployed | 8.7 | (not predictable without Pulse) | **lower than Experiment 1** (P01 and P09 have no exertion labels) |
| Classifier severity > 0.55 (frozen) | 30/30; 8.5 FA / 100 pd; 9/18 quiet series silent | strict 15/15, loose 15/15, FA 4.2 / 100 pd, 4/9 quiet series silent | **strict ≥ 26/30, FA ≤ 10 / 100 pd** |

**The strict (secondary) prediction is lower than Experiment 1.** P06 and P10 get exertion labels on days
1–3. That comes from the deliberate day-1 step (`SCENARIO_SIGNAL_DELTAS × 0.20`, documented in
`protocol_amendments.md`), which is unchanged. With the warm-up, those early labels can now
trigger exertion and an alert before onset. This is predicted, not a reason to change the
stories.

**Overall prediction:** fixing the EF band roughly doubles label accuracy and silences two of the
three should_stay_quiet patients. It does not fix the labels for the HFrEF-type stories (P04, P07).
The classifier's own severity at the frozen 0.55 threshold is predicted to still match or beat the
Pulse-based alert, so the paper's main finding would hold. Any outcome is reported as found.

## 7. How it is run

On the same Mac that ran Experiment 1 (Apple M5, Docker Desktop, `linux/amd64` image under
emulation; Experiment 1 runs took a median 31 min each), from a checkout of the commit that adds
this file, with all feature flags unset:

```bash
cp artifacts/results-v1/models/*.joblib models/ && shasum -a 256 -c docs/results-v1-models.sha256
docker compose build pulse-backend
# smoke test first: one dev-seed job (P01, seed 42) into a separate directory, never scored
docker compose run --rm --no-deps -v "$PWD:/workspace" \
  -e SCENARIO_TEST_COHORT=/workspace/config/scenario_tests/cohort_exp2.yaml \
  -e SCENARIO_TEST_OUTPUT_DIR=/workspace/results/scenario_tests/exp2_smoke \
  pulse-backend python -m src.evaluation.scenario_tests.run_patient_seed P01 42
# then the full batch
docker compose run --rm --no-deps -v "$PWD:/workspace" \
  -e SCENARIO_TEST_COHORT=/workspace/config/scenario_tests/cohort_exp2.yaml \
  -e SCENARIO_TEST_OUTPUT_DIR=/workspace/results/scenario_tests/exp2 \
  pulse-backend python -m src.evaluation.scenario_tests.run_batch
```

The smoke test must show the `warm-up day 1/1 … (not scored)` line and write its CSV before the
batch starts. Its output is not part of Experiment 2.

60 jobs (10 patients × seeds 48–53), up to 6 at a time, one process per job. Outputs:
`results/scenario_tests/exp2/daily_results_P??_seed??.csv`; logs in `exp2/logs/`; per-run SQLite
DBs in `exp2/dbs/` (gitignored). A job interrupted by sleep or overheating is rerun from day 1
(each starts from a fresh DB), and the interruption is noted in the results file.
